# 数字人动捕数据契约 v1

状态：已冻结供首轮联调使用。本文描述板端到电脑上位机的 UDP 数据，不直接绑定 Unity、VRM 或 VMC。

## 1. 已确认的板端输出

- 摄像头原始画面为 `1920×1080`，目标帧率为 60 FPS。
- 硬件预处理把画面缩放到 `626×352`，左右各补 7 像素，得到 `640×352` 网络输入。
- 姿态模型输出 COCO 17 点；面部模型输出 51 点。每个点均为网络坐标下的 `[x, y, confidence]`。
- 两个模型串行处理同一个输入消息，并共用同一个 `post_msg.meta`，所以一次后处理得到的 body 与 face 天然属于同一摄像头帧。
- 当前 `meta.timestamp` 来自 `system_clock::now().time_since_epoch().count()`，单位没有在类型中固定，不能直接作为跨设备协议时间戳。

网络坐标还原到原图归一化坐标时使用：

```text
x_norm = clamp((x_net - 7) / 626, 0, 1)
y_norm = clamp(y_net / 352,       0, 1)
w_norm = clamp(w_net / 626,       0, 1)
h_norm = clamp(h_net / 352,       0, 1)
```

## 2. v1 的范围

一个 UDP 数据报表示一个摄像头帧，最多携带一个人体和一张人脸。首轮联调按单人场景验收：人体和人脸各自选择检测置信度最高的结果。多人身份保持与跟踪不属于 v1。

协议只传检测结果，不在板端生成 VRM 骨骼旋转，也不在板端绑定任何具体角色模型。这样可以在电脑端独立迭代校准、平滑、IK 和 VMC 映射。

## 3. 传输约定

- 传输：UDP/IPv4，默认目标端口 `39540`。
- 当前联调地址：开发板 `192.168.126.49/24` → 上位机 `192.168.126.100/24:39540`。
- 字节序：小端。
- 浮点数：IEEE-754 `float32`。
- 每帧一个数据报；不拆包、不重传。上位机只保留最新合法帧。
- 完整 body + face 数据报固定为 900 字节，加上 IPv4/UDP 头仍小于常见 1500 字节 MTU，不会发生 IP 分片。
- 包尾使用 CRC32 校验协议内容；UDP 校验和仍由系统网络栈负责。

## 4. 固定头部（40 字节）

| 偏移 | 类型 | 字段 | 说明 |
|---:|---|---|---|
| 0 | `char[4]` | magic | 固定为 ASCII `DMV1` |
| 4 | `uint8` | version | 固定为 1 |
| 5 | `uint8` | flags | bit0=body，bit1=face，bit2=坐标已归一化 |
| 6 | `uint16` | header_bytes | 固定为 40 |
| 8 | `uint32` | packet_bytes | 含包尾 CRC 的总字节数 |
| 12 | `uint32` | sequence | 每发送一帧加 1，溢出后自然回绕 |
| 16 | `uint64` | capture_time_ns | 板端时钟域下的采集时刻，纳秒 |
| 24 | `uint64` | emit_time_ns | 同一板端时钟域下的发送时刻，纳秒 |
| 32 | `uint16` | frame_width | 原图宽度，当前为 1920 |
| 34 | `uint16` | frame_height | 原图高度，当前为 1080 |
| 36 | `uint8` | pose_count | 无人体为 0，有人体为 17 |
| 37 | `uint8` | face_count | 无人脸为 0，有人脸为 51 |
| 38 | `uint8` | source_id | 摄像头编号，当前为 0 |
| 39 | `uint8` | reserved | 固定写 0，接收端忽略 |

`capture_time_ns` 与 `emit_time_ns` 只能互相相减，用来计算板端处理耗时。板端和电脑的时钟没有共同原点，电脑不能直接用自己的接收时间减去它们来计算网络延迟。当前板端实现把已有的 `system_clock` 采集时间显式换算为纳秒，并用同一时钟生成发送时间。

## 5. 可选检测块

检测块按 `body`、`face` 的顺序紧跟头部。对应 flag 未置位时，该块完全省略。

每个检测块先写 20 字节检测信息：

```text
float32 detection_score
float32 bbox_x
float32 bbox_y
float32 bbox_w
float32 bbox_h
```

随后按固定顺序写关键点，每点 12 字节：

```text
float32 x_norm
float32 y_norm
float32 confidence
```

所有坐标、检测分数和置信度都在 `[0, 1]`。低置信度点仍保留其坐标，是否采用由上位机按置信度门控决定。

数据块大小：

- body：`20 + 17×12 = 224` 字节。
- face：`20 + 51×12 = 632` 字节。
- 包尾：前面所有字节的 CRC32，`uint32`，4 字节。

合法总长度只有四种：44（空帧）、268（仅 body）、676（仅 face）、900（body + face）。

## 6. 关键点顺序

### COCO 17 人体点

```text
0 nose                 1 left_eye            2 right_eye
3 left_ear             4 right_ear           5 left_shoulder
6 right_shoulder       7 left_elbow           8 right_elbow
9 left_wrist          10 right_wrist         11 left_hip
12 right_hip          13 left_knee           14 right_knee
15 left_ankle         16 right_ankle
```

### 内脸 51 点

51 点来自标准 68 点布局的原索引 `17..67`，即去掉 17 个下颌轮廓点：

| v1 索引 | 原 68 点索引 | 区域 |
|---|---|---|
| 0..4 | 17..21 | 右眉 |
| 5..9 | 22..26 | 左眉 |
| 10..18 | 27..35 | 鼻部 |
| 19..24 | 36..41 | 右眼 |
| 25..30 | 42..47 | 左眼 |
| 31..42 | 48..59 | 外嘴唇 |
| 43..50 | 60..67 | 内嘴唇 |

这里的左右均指被拍摄者自身的左右。

## 7. 接收端规则

接收端必须依次检查 magic、版本、头部长度、总长度、flags/count 一致性、CRC32 和所有数值是否有限且位于 `[0, 1]`。任一检查失败就丢弃整个数据报。

接收端以 `source_id + sequence` 判断新旧和丢帧，不等待缺失数据报。超过约 150 ms 没有收到新帧时，角色控制量应逐渐回到中性值，而不是保持最后一个动作。

## 8. 已知边界

- 当前人体模型只给出 2D 点，没有深度和关节旋转。上位机可以通过人体比例、时间连续性和 IK 得到可用的 2.5D 动作，但无法从单帧 2D 数据唯一恢复真实 3D 姿态。
- 51 个面部点足以计算眨眼、张嘴、眉毛和近似头姿；首轮仍需做每位使用者的中性表情校准。
- v1 不含手指、眼球注视、多人 track id、相机内参和可靠传输。需要时通过新版本扩展，不能改变 v1 字段含义。

## 9. 首轮联调验收

1. 板端每个后处理帧最多发一个 900 字节数据报。
2. 电脑端连续接收时，CRC 错误为 0；允许 UDP 丢帧但程序不得卡住或积压旧帧。
3. `sequence` 单调递增，body 与 face 来自同一 sequence。
4. 还原后的鼻尖、肩、腕、眼角和嘴角能叠加回原始 1920×1080 画面的正确位置。
5. 静止 10 秒时记录平均帧率、丢帧率、板端处理耗时 `emit_time_ns-capture_time_ns` 和电脑接收间隔。
